# Stage10: ограничения и планы выполнения

Входные гипотезы перечислены в BASELINE_AUDIT, методика — LOAD_TEST_PLAN. `reports/stage10/sql-plans-initial.json`: EXPLAIN(ANALYZE,BUFFERS,FORMAT JSON), отдельный лабораторный PG. На первоначальном объёме pending count .369ms, latest DISTINCT ON1.418ms, replay lookup .009ms, control row lock .021ms, outbox ready select .030ms, observation order .015ms, transition history .012ms. Это одиночные диагностические measurements, не tail latency под конкуренцией. Диагностические selects не идентичны полному ingestion transaction или worker claim/update; не выдавать их длительность за transaction latency.

Особенности архитектуры: глобальный admission advisory lock + shared security-capacity row lock; pending count сканирует status/историю; одна relay claim/store/finish на строку; PostgreSQL1CPU и receiver/relay по.5CPU; Policy/monitoring конкурируют за тот же PostgreSQL. Latest selection сортирует накопленную историю; аддитивный индекс мог бы помочь на больших объёмах, но пока измерение не подтверждает необходимость. Нет оснований менять crypto/security guarantees ради throughput.

Старая capacity Outbox — защита памяти/хранилища, не число поддерживаемых устройств. Нельзя экстраполировать из3/10/25 на10k. Один run/cohort не даёт предельную capacity или CI для независимых deployments. Частота .5s соответствует целевым6/20/50msg/s; наблюдаемая source generation может быть ниже из-за scheduler/device-budget. Это нужно отделять от потери уже сформированных сообщений.

На Stage10 пока не внесены SQL migrations/indexes: исторические migrations сохранены. Повторные актуальные monitoring query plans и Mongo history explain сохраняются отдельно по выросшей истории. Если API укладывается в budget, index migration без измеренного выигрыша не нужна. PG commit timing и network-only latency не инструментированы: timestamp admission и post-Mongo finish — другие интервалы.

## Подтверждённое ограничение Policy

`medium-policy-inflight.json`: 11723 security observations,6120 consumed,5603 pending, source lag последнего решения112.697s при25×2msg/s. Default worker batch32 и sleep1s создают верхнюю оценку≈32 processed events/s ещё до стоимости SQL; вход≈50/s её превосходит. Это не MQTT failure. В `policy-freshness-before.json` worker heartbeat ready и state updated недавно, но last_event_at старше207s, p.stale=false. Исправлен read-only freshness adapter: учитывает время реально учтённого события с TTL правил, missing/future также stale. Новые поля и DOM не меняют FSM/Policy commands.

Default batch не увеличен ради более красивых результатов. Настройка batch до128 допустима существующим config, но должна измеряться отдельно с влиянием на PG/admission, fairness и source age; это не обещание пропускной способности. Другие будущие оптимизации: уменьшить повторные round-trips Policy на событие, batch-consume с сохранением exact-once и immutable decisions; только с дополнительным regression coverage. Нельзя пропускать security events или менять семантику FSM ради скорости.

## Query evidence на выросшей истории

После25-device stability `medium-monitoring-plans.json` содержит26 фактических SELECT карточки (SQLAlchemy execution capture, затем EXPLAIN ANALYZE BUFFERS), наиболее длительный29.868ms на данном снимке. Mongo `medium-storage.json`: bounded history50 возвращает50, examines50 keys/50 documents, использует существующие indexes. Relay не получил listIndexes privileges; отдельный admin diagnostic прочитал plan внутри нового Mongo project. Новая migration/index не добавлена, старые schema/data не изменены. PostgreSQL max_connections100, фактически snapshot connections сохраняются в каждом sample.

Pending Policy select вырос с6.500ms при11723 observations до25.695ms на конце medium diagnostics; это фактический NOT EXISTS запрос с PKlookup по consumed signals, а не только batch/sleep. На extended history меньшего объёма select9.618ms. Полный monitoring SELECT максимум19.842ms после50-device окна; это **не** доказательство ускорения при большем N — durations/history sizes различаются. Индекс «наугад» не устраняет повторный поиск непрочитанного события через растущий consumed prefix; cursor/batching потребуют отдельного доказательства семантики late events/version activation.
