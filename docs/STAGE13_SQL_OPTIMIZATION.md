# SQL optimization and measurement boundaries

Source search formerly repeats a version-scoped NOT EXISTS over security_observations for every event, ordered occurred_at/id. The existing indexes are preserved.0011 adds policy_pending(kind,sort_at,event_id), processing-time index policy_signals(version,created_at), singleton persisted schedule and worker metrics JSON. No old migration is rewritten; no cryptographic state table altered.

The recurring full-history lookup is replaced with two bounded ordered pending selects per transaction, then at most32 source process() calls. Completion remains the existing unique(event_id,version) marker. Seed anti-joins run at activation/upgrade, not once per source event. Queue entries are created in the source transaction without the policy advisory lock. No timestamp cursor can hide a late commit.

`query-plans-before.json`: independent private diagnostic schema,1k/10k/50k/100k source history,32 pending, three actual EXPLAIN(ANALYZE,BUFFERS,FORMAT JSON) captures/query. First old query1.058/12.354/69.643/146.109ms versus pending0.027/0.030/0.034/0.033ms. Diagnostic rows have reduced shape: not the entire receiver transaction, not an ingestion benchmark. Actual full-row plans on accumulated real journals are additionally stored in each ledger-final.json. Empty post-drain pending plans are labelled as such, never substituted for nonempty lookup scaling.

Matched-input ablation:1000 initial consumed source identities and1000 identical new events, same0011 physical schema, explicit evaluation clock, ten devices, three fresh schemas per case. These are **synthetic SQL/processor fixtures**, not fake MQTT admissions. Results in ablation.json: median24.22events/s original32+sleep1,100.09 removing idle sleep,232.74 indexed queue with one-event transactions,30.40 batch32 retaining sleep1,433.00 batch32 with bounded adaptive polling. All final FSM hashes match. The controlled clock represents older evidence; no interpretation as fresh live sensor data.

A separate paired cached/uncached experiment retains transaction/queue/order but forces the original per-event Rules lookup/parse. Counts7.202→8.202 instrumented calls/event confirm one extra lookup per event; three actual per-run timings retained in ablation-cache-control.json. Different timing batches are not pooled to manufacture a precise universal speedup. Primary timings omit bootstrap/heartbeat and use common physical schema; live runs retain their real startup, heartbeat and0010/0011 differences.

SQLAlchemy cursor hooks count client execute calls and their observed duration. They do **not** count driver-internal pre-ping, PostgreSQL trigger statements or all server transactions. Application commit events measure processing transactions; the event fires before DBAPI commit, so its timing excludes final fsync. Separate poll wall and receiver engine.begin wall include successful context exit/commit. No approximate subtraction produces server CPU/commit time.

Controlled batching changes processing commits1000→32 for1000 events, not a promise that every live batch is full. Live idle/heartbeat/partial batches have their own measured denominator. PostgreSQL xact_commit/xact_rollback/numbackends/lock waits include other components and probes and are reported separately. Query-plan repeats are warm observations, not independent deployments or confidence intervals.

Maximum32 source entries, up to32 claims/source,250ms soft limit checked between entries, existing5s statement/2s lock deadlines. Per-source clock is still read individually; no single batch-wide now. Version activation/prune share the transaction lock. Transient source/metadata DDL during upgrade may delay admission; a stop-old-workers/migrate/start-new-workers rollout is required. Mixed old/new binaries are unsupported.
